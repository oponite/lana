# LIP-032: Durable future messages

- **Status:** Final
- **Author:** Vijay Neelakantan
- **Date:** 2026-09-24

## Motivation

An application needs to save a message now and make it available after a
specified time or named event. Delivery must remain under application control:
Lana cannot infer that an event occurred or send a notification on its own.

## Specification

- `std/future_messages` provides `create`, `inspect`, `check`, `receive`,
  `acknowledge`, and `cancel`. The application opens a store and calls `check`
  on startup, on relevant events, or on a timer. Stopping the application
  stops checks; missed events require explicit replay.
- A message has a stable caller-supplied ID, a definite JSON-compatible
  payload, provenance references, and a condition containing a nonnegative
  `not_before_utc` time, a named event, or both. Event comparisons use exact
  scalar values and explicit operators. There is no prose interpretation or
  implicit sampling.
- `check` validates all pending messages before changing any. Each match
  advances one message to `ready` in an atomic store revision with a receipt
  recording the match time, context ID, condition, and exact store revision.
  `receive` lists ready messages without acknowledging them.
- `pending`, `ready`, `acknowledged`, and `cancelled` survive restart. Repeated
  identical calls do not create another transition. Cancellation cannot undo
  acknowledgment, and a clock rollback cannot undo readiness.
- IDs, payloads, comparison lists, context fields, page sizes, pending counts,
  and stored records have the bounds in `spec/SPEC.md`. Invalid input and
  resource exhaustion fail before staging a transition. Unrelated staged
  store writes block a transition. After an uncertain commit, callers reopen
  the store and inspect the stable ID before retrying.
- The Rust runtime uses host-call ID 188. This adds no opcode or bytecode
  version. The inbox has no daemon, notification, or external action.

## Rationale

The existing durable store supplies the necessary atomic transitions. An
application-controlled check makes the release event inspectable and avoids
claiming that Lana can deliver while the application is stopped.

## Compatibility

Existing source and LABC v1-v5 retain their behavior. The new standard module
is opt-in. The Rust-only Lana 4.0 runtime owns the host call; no C API or
plugin is added. Message results use LIP-029 record schema v1.

## Test coverage

- Source and Rust tests cover time and event release, combined conditions,
  missing fields, invalid schemas, and limits.
- Restart tests cover ready, acknowledged, and cancelled states, replay,
  idempotence, clock rollback, and paged receive.
- Store tests cover staged-write conflicts and commit-I/O reconciliation.
- No message operation performs network or notification I/O.
