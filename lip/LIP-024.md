# LIP-024: Async I/O and a deterministic event loop

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana's task primitive forks an independent VM per task — that is CPU
parallelism, not async I/O. A program that waits on ten network calls (LIP-019)
would fork ten VMs, each blocked on a socket, paying a full VM heap and budget
per wait. Python's universality for network-bound work comes from `asyncio`:
thousands of concurrent I/O operations on one thread. A language that can only
parallelize by forking VMs cannot do the service-health and routing work that is
its own domain.

This LIP adds cooperative async: `async` functions, `await`, and a
deterministic single-threaded event loop. It is distinct from the forked-VM
task primitive and preserves it.

## Specification

### 1. Syntax

```lana
async fn fetch_all(urls) {
    let results = [];
    for url in urls {
        let resp = await http_get(url);
        results = push(results, resp);
    }
    return results;
}

let fut = fetch_all(urls);
let results = await fut;
```

- `async fn` declares an async function; calling it returns a future and does
  not execute the body.
- `await` suspends the current task and yields to the event loop; the task
  resumes when the awaited future completes.
- `await` is only valid inside an `async fn`; using it elsewhere is a
  compile-time error.

### 2. Futures

- A future is a first-class value. `future_all(futures)` completes when all
  complete; `future_race(futures)` completes with the first to complete.
- `sleep(ms)` returns a future that completes after `ms` milliseconds.
- An awaited host call that is `io` (e.g. `http_get`) returns a future when
  awaited; the event loop drives the underlying I/O.

### 3. Event loop

- The event loop is a **single-threaded cooperative scheduler** in the VM.
  Async tasks are lightweight frames, not forked VMs — they share one heap and
  one budget, distinct from the existing forked-VM task primitive.
- Scheduling is **deterministic**: given a fixed set of futures and a fixed
  seed, the order of resumptions is reproducible. RNG streams are per-task
  (already the case).
- A task that never awaits and never yields is a cooperative hog; the
  instruction budget still bounds it.

### 4. Effects

- An async function is an `io` effect (it can await I/O). A `pure` context
  cannot call an async function without an explicit boundary.
- Cancellation: a future can be cancelled; a cancelled task's effects are not
  executed (consistent with the planned-effect model).

## Rationale

- **Cooperative async, not threads.** Forking a VM per I/O wait is the wrong
  cost model. Cooperative frames share a heap and budget, which is what makes
  thousands of concurrent waits feasible.
- **Deterministic scheduling.** Lana's premise is reproducibility. A
  non-deterministic scheduler would make a network-bound program's behavior
  unreproducible; a deterministic scheduler keeps it auditable.
- **Distinct from forked-VM tasks.** CPU parallelism and I/O concurrency are
  different problems; Lana keeps both primitives rather than conflating them.

## Compatibility

- **New syntax** (`async fn`, `await`) — this LIP changes source syntax and
  must satisfy `spec/SYNTAX.md`.
- **New LABC encoding** for async frames and `await` suspension; the bytecode
  version advances (v2 → v3) with a dual-version loader.
- **Existing forked-VM task primitive is preserved.**
- **Resource limits unchanged**; async frames count against the memory limit.

## Test coverage

- Concurrent I/O: many `await http_get` calls complete concurrently on one
  thread.
- Determinism: the same futures and seed produce the same resumption order.
- `await` outside `async fn` is a compile-time error.
- Cancellation: a cancelled future does not execute its effects.
- `future_all`/`future_race` semantics.
