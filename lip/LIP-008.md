# LIP-008: Uncertainty-carrying tensors

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

`spec/ML.md` already mandates that every ML operation returns its prediction
together with its uncertainty, and that the uncertainty is never discarded or
coerced into an ordinary value. This LIP extends that discipline to uncertain
operands and ML results: an op over uncertain inputs, or an ML result, returns
prediction + uncertainty. Ordinary tensor math over certain inputs stays
ordinary (Decision 3).

Python bolts uncertainty on awkwardly — Bayesian layers, ensembles, MC dropout
— each a separate, opt-in mechanism that does not compose and does not survive
a training loop. Lana would have it as the default: uncertainty is a first-class
part of every tensor value, propagated automatically through every operation,
and flowing through provenance and audit. This is native, uncertainty-aware ML,
not a bolt-on.

## Specification

### 1. Uncertainty-carrying tensor

An op over uncertain operands, or an ML result, returns a structured value, not
a bare tensor:

```lana
let r = matmul(a, b);   // r is { prediction, uncertainty }
let p = r.prediction;   // the point estimate (a tensor)
let u = r.uncertainty;  // the uncertainty (a tensor of the same shape)
```

- `prediction` is the ordinary tensor result (LIP-004).
- `uncertainty` is a tensor of the same shape carrying, per element, a
  distribution summary — a variance for a Gaussian summary, or a full
  distribution where the operation requires it. A `STATE` tensor (LIP-007) is
  one valid uncertainty representation; the discipline does not fix the
  representation.
- Certain inputs produce an ordinary tensor, not an `Uncertain<Tensor>`; the
  discipline is enforced only where uncertainty is present, so a downstream op
  cannot silently assume certainty about an uncertain value.

### 2. Type discipline

- The compiler tracks the uncertainty-carrying type; an op over uncertain
  operands (or an ML result) is `Uncertain<Tensor>`, and using it where a bare
  `Tensor` is expected is a compile error. Ordinary tensor ops over certain
  inputs remain `Tensor`.
- Extracting `prediction` is an explicit act that acknowledges the uncertainty;
  it does not erase provenance (the uncertainty remains in the derivation).
- This mirrors the existing effect discipline (`pure`/`observation`/`stochastic`
  in `compiler/resolver.lana`): uncertainty is a property the compiler enforces,
  not a runtime convention.

### 3. Automatic uncertainty propagation

Uncertainty flows through operations by the standard error-propagation rules,
exactly as gradients flow through autodiff (LIP-011):

- Element-wise `+ - * /`: variance propagates by the usual first-order rules.
- `matmul`: variance propagates through the contraction.
- Reductions (`sum`, `mean`): variance aggregates over the reduced axes.
- `append`/`measure`/`transform` (LIP-005, LIP-007): uncertainty propagates
  through the probabilistic operation's own law.

The propagation is exact for the chosen summary (e.g. first-order for a
Gaussian summary) and is a property of the operation, not a hidden runtime
choice.

### 4. Provenance and audit

- The uncertainty is part of the value's derivation, so it is auditable: you
  can ask *which input's uncertainty produced which output's uncertainty*.
- Deterministic replay (§9.7.5) covers the uncertainty: the same
  `(seed, inputs, version)` reproduces the same prediction and uncertainty
  bytes.
- A training run (LIP-006) over uncertainty-carrying tensors therefore yields a
  model whose predictions carry uncertainty end to end, with the uncertainty
  traceable to its source.

### 5. Errors

| Condition | Error |
|---|---|
| using an `Uncertain<Tensor>` where a `Tensor` is expected | compile error |
| `uncertainty` on a bare (certain) tensor | `LANA_ERR_TYPE` |
| non-finite uncertainty after propagation | `LANA_ERR_INVALID_PARAMETERS` |

## Rationale

- **Default, not bolt-on.** Python's Bayesian layers, ensembles, and MC dropout
  are separate mechanisms that do not compose. Making uncertainty a type
  discipline means uncertain operands and ML results carry it, and it composes
  for free.
- **Inherited, not invented.** The discipline reuses the existing effect system
  and the ML.md mandate; the propagation reuses the autodiff tape's structure
  (LIP-006). No new propagation engine is needed.
- **Auditable by construction.** Because uncertainty is a value with provenance,
  it is inspectable and replayable — the same properties that make Lana's
  decisions auditable.

## Compatibility

- **No new `ValueType` tag** — an uncertainty-carrying tensor is a structured
  value (a map/ADT) over `VAL_TENSOR`, per the ML.md mandate.
- **No LABC format change** — operations are host calls, so the bytecode
  version stays `2`.
- **Depends on LIP-004** (tensor); complementary to LIP-007 (a `STATE` tensor
  is one uncertainty representation).
- **Resource limits unchanged**; the parallel uncertainty buffer counts against
  the 256 MiB limit.

## Test coverage

- An op over uncertain operands (or an ML result) returns
  `{ prediction, uncertainty }`; ordinary tensor ops over certain inputs stay
  ordinary.
- Error propagation: element-wise, `matmul`, and reductions against hand-computed
  first-order variances.
- `append`/`measure`/`transform` propagate uncertainty through their own laws.
- Compile error when an `Uncertain<Tensor>` is used as a bare `Tensor`.
- Provenance: the uncertainty of an output traces to its input.
- Differential conformance: byte-identical C11 vs Rust output for a fixed seed.
