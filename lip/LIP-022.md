# LIP-022: Rich collections, generators, and comprehensions

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana has arrays and maps but no set, no comprehensions, and no lazy iterators.
Every filter-map-reduce is a hand-written loop. Python's ergonomic core is its
collections and its comprehension/generator syntax — the reason a Python
program is half the length of the equivalent C. A language that makes the
common data-shaping operations verbose is not universal.

This LIP adds a set type, lazy generators, and comprehension syntax. It is the
one universality LIP that changes source syntax, so it must satisfy
`spec/SYNTAX.md` in addition to the authority order. Generators map naturally
onto Lana's existing lazy philosophy (`STATE_DIST`, `Dataset`).

## Specification

### 1. Set type

```lana
let s = set_new();
set_add(s, 1);
let has = set_contains(s, 1);   // true
let u = set_union(a, b);
let i = set_intersect(a, b);
let d = set_difference(a, b);
```

- A set is a hash set of ordinary values. `STATE`, `STATE_DIST`, and
  `Information` are not set members (they have no canonical hash); inserting one
  raises `LANA_ERR_TYPE`.
- Set operations are `pure` and return new sets; they do not mutate.

### 2. Generators

> **Status:** Implemented (LABC v3). `yield`/`next` and suspendable generator
> frames are live; the bytecode version advances to v3 only for programs that
> contain generators. Sets (§1), comprehensions (§3), and iterators (§4) remain
> deferred.

```lana
fn naturals() {
    let n = 0;
    loop {
        yield n;
        n = n + 1;
    }
}

let it = naturals();
let first = next(it);   // Result<number, E> — Ok(0)
```

- A function containing `yield` is a generator; calling it returns a lazy
  iterator and does not execute the body.
- `next(it)` returns `Result<T, E>`: `Ok(value)` for the next value, an
  exhausted error when the generator returns.
- Generators are lazy by default; no value is computed until `next` is called.
  This matches the `STATE_DIST`/`Dataset` laziness contract.

### 3. Comprehensions

```lana
let squares = [x * x for x in [1, 2, 3]];        // [1, 4, 9]
let evens   = [x for x in xs if x % 2 == 0];     // filtered
let keys    = {k for k in m};                    // set comprehension
let pairs   = {k: v for k, v in entries};        // map comprehension
```

- Comprehension syntax is `[expr for x in iterable]` with an optional
  `if pred` guard. The keywords `for`, `in`, and `if` are reused; no novel
  symbols are introduced (SYNTAX-5).
- A comprehension is sugar for a generator plus a collector; it lowers to the
  generator form, so there is one canonical implementation (SYNTAX-2).

### 4. Iterators

```lana
let it = iter([1, 2, 3]);
let doubled = map(fn(x) { x * 2 }, it);
let kept = filter(fn(x) { x > 1 }, it);
let total = reduce(fn(acc, x) { acc + x }, it, 0);
let zipped = zip(a, b);
let indexed = enumerate(a);
```

- `map`, `filter`, `zip`, and `enumerate` return lazy iterators; `reduce`
  consumes eagerly and returns a value.
- `for x in iterable` consumes any iterator, not just arrays.

## Rationale

- **Generators are the lazy primitive Lana already believes in.** `STATE_DIST`
  and `Dataset` are lazy; a generator is the same idea for ordinary values.
  One laziness model, not two.
- **Comprehensions lower to generators.** This keeps one canonical form
  (SYNTAX-2) and avoids a second implementation of the same semantics.
- **Explicit keywords, no novel symbols.** `for`/`in`/`if` are already Lana
  keywords; comprehensions reuse them rather than inventing `|` or `->`
  (SYNTAX-5, SYNTAX-8).

## Compatibility

- **New syntax** (`yield`, comprehensions) — this LIP changes source syntax and
  must satisfy `spec/SYNTAX.md` (SYNTAX-1..12 + Acceptance Principle).
- **New LABC encoding** for generator frames and comprehension lowering; the
  bytecode version advances (v2 → v3) with a dual-version loader, or the
  constructs lower to existing opcodes where possible.
- **New host calls** for set operations appended to `LanaHostCallId`.
- **Resource limits unchanged**; a generator's laziness does not exempt it
  from the instruction budget.

## Test coverage

- Set: add/contains/union/intersect/difference; `STATE` insertion rejected.
- Generator: laziness (body does not run until `next`), exhaustion, `yield` in
  a loop.
- Comprehension: list/set/map forms, filtered form, lowering equivalence to
  the generator form.
- Iterators: `map`/`filter`/`zip`/`enumerate` laziness, `reduce` result.
- SYNTAX conformance: each construct passes the five Acceptance-Principle
  checks.
