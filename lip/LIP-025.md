# LIP-025: WebAssembly and embedded target

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana runs as a native binary on macOS and Linux. Python runs everywhere —
desktop, server, browser (Pyodide), edge, and serverless — and that ubiquity is
a large part of its universality. A language that only runs where its native
binary is installed cannot be the default anywhere.

The canonical VM is Rust (`lana-vm`, `lana-runtime`, `lana-bytecode`), which
compiles to WebAssembly. This LIP adds a `wasm32` target and a host binding so
Lana runs in the browser, on edge runtimes, and in serverless functions. It
adds no language semantics; it is a build target plus a host-call policy.

## Specification

### 1. Build target

- Compile the Rust VM crates to `wasm32-unknown-unknown` (browser) and
  `wasm32-wasi` (edge/serverless).
- The compiler and bytecode are unchanged: the same Lana source produces the
  same LABC v2, which the WASM VM executes identically to the native VM.

### 2. Host binding

- A JS/TS package `lana-wasm` exposes:

  ```js
  const { run, runBytecode, measure, sample } = await import("lana-wasm");
  const result = run(source);          // compile + run
  const out = runBytecode(labcBytes);  // run precompiled LABC
  ```

- The binding is a thin wrapper over the WASM exports; it does not reimplement
  the language.

### 3. Host-call policy

- Filesystem and network host calls are **unavailable by default** in WASM
  (there is no ambient FS or net). A program that calls `directory_list` or
  `http_get` fails with `LANA_ERR_UNSUPPORTED_OPERATION` unless the host
  explicitly provides those functions.
- The host provides capabilities explicitly: `lana-wasm` accepts a
  `capabilities` map naming which host calls are wired to host-provided
  functions. This is the same capability model as LIP-012, applied to the
  embedding boundary.

### 4. Determinism and limits

- The WASM build is deterministic: the same source and seed produce the same
  result as the native VM.
- Resource limits (256 MiB, 50,000,000 instructions) are enforced in WASM via
  bounded `memory.grow` and an instruction counter.

## Rationale

- **Rust already targets WASM.** The canonical VM is Rust; this is a build
  target, not a rewrite. The C11 reference VM is unaffected.
- **Capability-gated host calls.** A browser or edge runtime must not grant
  ambient filesystem or network access. Making host calls opt-in per embedding
  matches secure-by-default and LIP-012.
- **Same bytecode, same result.** The value of a WASM target is that a decision
  computed in the browser is byte-identical to one computed on a server. That
  is only true if the VM is the same; this LIP keeps it the same.

## Compatibility

- **New build target** (`wasm32-unknown-unknown`, `wasm32-wasi`); no change to
  the native build.
- **No LABC change, no language change.**
- **Host-call availability differs by target** and is documented; a program
  that uses unavailable host calls fails explicitly, never silently.
- **Resource limits unchanged.**

## Test coverage

- Run the reference examples in WASM and compare results to the native VM
  (byte-identical).
- Determinism: same source + seed → same result across native and WASM.
- Host-call gating: `directory_list`/`http_get` fail with
  `LANA_ERR_UNSUPPORTED_OPERATION` when not provided; succeed when wired.
- Resource-limit enforcement: a program that exceeds the instruction budget
  fails in WASM as it does natively.
