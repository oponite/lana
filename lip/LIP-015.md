# LIP-015: The Dataset Engine — relational algebra, persistence, and provenance over lazy data

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana has a lazy dataset primitive (`spec/DATASETS.md`: `lazy(fn, bound)`,
`force`, `force_all`) but no way to *query* it. Filtering, joining, grouping,
and aggregating over data is hand-written per program, and there is no
persistence, no transactions, and no planner — the moment a dataset outgrows
memory or needs to survive a crash, Lana flattens into a homemade SQL.

This LIP adds a **Dataset Engine**: a source-agnostic `Dataset` abstraction with
a lazy-by-default relational algebra, a persistent storage engine with
transactions, a planner, and provenance. It is the data layer that the training
(LIP-006), incremental learning (LIP-010), and capability (LIP-012) LIPs all
consume.

## Specification

### 1. The `Dataset` abstraction

- A new `ValueType` tag `VAL_DATASET`: a source-agnostic collection of rows.
- `lazy` stays a **source**, not a storage engine. A `Dataset` is built over one
  of several sources: `lazy` (the existing generator), in-memory, disk, or an
  external adapter. The source is an implementation detail behind one surface.
- The algebra is **lazy-by-default from the first node**: a query builds a plan,
  not a materialized result, so Lana's "potentially unresolved information
  source" model is preserved rather than flattened into eager SQL.

### 2. Relational algebra

```lana
let ds  = dataset(lazy(fn, bound));          // wrap a source
let a   = filter(ds, pred);                  // row predicate
let b   = map(ds, f);                        // row transform
let c   = select(ds, ["x", "y"]);            // projection
let d   = limit(ds, 100);                    // take first N
let e   = sort(ds, "x");                     // order by key
let g   = group_by(ds, "k");                 // group rows by key
let h   = aggregate(g, sum("v"));            // reduce a group
let j   = join(a, b, on: "k");               // equi-join
let m   = materialize(ds);                   // force the plan to a value
```

- `filter`, `map`, `select`, `limit`, `sort`, `group_by`, `aggregate`, `join`,
  and `materialize` are host calls over `VAL_DATASET`.
- Each operation returns a new `Dataset` (a plan node); only `materialize`
  forces evaluation. `force`/`force_all` (existing) materialize a single element
  or the bounded prefix.
- `aggregate` accepts numeric reductions (`sum`, `mean`, `max`, `min`, `count`)
  and, over `STATE`/`STATE_DIST` rows, **STATE-aware aggregation** — combining
  evidence by the existing `append` law rather than a numeric sum.

### 3. Persistence and transactions

- A `Dataset` may be persisted to a storage engine with a write-ahead log (WAL),
  crash recovery, and revisions.
- Transactions are atomic: a batch of writes commits as one revision or not at
  all. Recovery replays the WAL to the last committed revision.
- Revisions are the existing replay contract (`EVIDENCE.md` §5): a committed
  revision is byte-identical for the same `(seed, inputs, version)`.

### 4. Planner

- The planner rewrites a query plan using statistics: predicate pushdown,
  projection pushdown, and join ordering.
- `explain(ds)` returns the plan as an ordinary value, so the chosen plan is
  inspectable and auditable, not a hidden optimizer choice.

### 5. Provenance, MVCC, and adapters

- Every `Dataset` node carries provenance: a row's derivation records which
  source and which operations produced it.
- MVCC gives readers a consistent snapshot of a committed revision while writers
  commit new ones.
- External adapters (files, databases) are sources behind the same `Dataset`
  surface; an adapter is a host-call boundary, not a new opcode.

### 6. Errors

| Condition | Error |
|---|---|
| operation on a non-`Dataset` value | `LANA_ERR_TYPE` |
| `join` on incompatible keys | `LANA_ERR_INVALID_PARAMETERS` |
| `aggregate` over a non-numeric, non-`STATE` column | `LANA_ERR_TYPE` |
| `materialize` exceeds the materialization bound | `LANA_ERR_LIMIT` |
| transaction conflict (concurrent commit) | `LANA_ERR_CONFLICT` |
| WAL recovery fails (corrupt log) | `LANA_ERR_CORRUPTION` |
| `explain` on a non-`Dataset` value | `LANA_ERR_TYPE` |

## Rationale

- **A source, not a storage engine.** `lazy` remains the generator it is; the
  `Dataset` abstraction sits above it, so in-memory, disk, and adapters are
  peers rather than a rewrite of `lazy`.
- **Lazy-by-default, not eager SQL.** The algebra builds a plan, so a query over
  an infinite lazy dataset is valid until materialized — the same bounded
  materialization discipline as `spec/DATASETS.md`.
- **Provenance and replay are inherited.** The engine reuses the existing
  derivation DAG and replay contract rather than inventing a parallel system, so
  a query result is auditable and replayable like every other Lana value.
- **STATE-aware aggregation is the tie-in.** Aggregating over `STATE` rows
  combines evidence by the existing `append` law, so the data layer speaks the
  language's uncertainty model instead of reducing it to numbers.

## Compatibility

- **New value type** `VAL_DATASET`; `VAL_LAZY` is unchanged (a source behind it).
- **No LABC format change** — the algebra, `materialize`, and `explain` are host
  calls, so the bytecode version stays `2`.
- **New host-call IDs** appended to `LanaHostCallId` (C and Rust must match).
- **Depends on LIP-004** (tensor, for numeric aggregation), the existing `lazy`
  (`spec/DATASETS.md`), and the replay contract of `EVIDENCE.md` §5.
- **Resource limits unchanged**; a `Dataset` plan and materialized rows count
  against the 256 MiB limit.

## Test coverage

- Each algebra operation against known results (filter, map, select, limit,
  sort, group_by, aggregate, join).
- Lazy-by-default: a query over an infinite lazy dataset is valid until
  `materialize`; `materialize` over the bound raises `LANA_ERR_LIMIT`.
- STATE-aware aggregation: `aggregate` over `STATE` rows matches the `append`
  law.
- Persistence: a committed revision survives a simulated crash and WAL recovery.
- Transactions: a conflicting commit raises `LANA_ERR_CONFLICT`; a batch commits
  atomically.
- `explain` returns an inspectable plan; pushdown is observable in the plan.
- Provenance: a row's derivation traces to its source and operations.
- Differential conformance: byte-identical C11 vs Rust output for a fixed seed.
