# LIP-029: Meaning-preserving records and execution boundary

- **Status:** Accepted
- **Author:** Lana maintainers
- **Date:** 2026-09-15

## Motivation

Lana must cross process and FFI boundaries without turning unresolved values,
claims, authorization, or action outcomes into ordinary JSON with lost meaning.
It also needs one narrow way to execute a real-world action without making
arbitrary network access equivalent to authorization.

## Specification

- A record has independent `record_schema` and bridge ABI versions. It contains
  a stable ID, kind, transport status, domain status, typed payload or error,
  evidence, assumptions, uncertainty/exactness, and metadata. Action records
  additionally carry their plan digest, capability identity, authorization ID,
  and receipt status.
- The Rust FFI exchanges length-delimited UTF-8 record JSON and opaque handles.
  It exposes a numeric ABI version, struct-size guards for fixed C inputs, and
  one documented free function for returned buffers. Rust layouts never cross
  the ABI.
- `std/execution.plan_webhook(path, payload)` accepts a relative path and a
  definite JSON-compatible payload. `execute(capability, authorization, plan)`
  requires an `Authorize` decision bound to the plan digest and capability ID.
- An opaque execution capability has one canonical HTTPS origin. The host, not
  Lana, resolves its credential key ID and encrypted host metadata. Source,
  bytecode, records, FFI values, logs, and receipts never contain raw secrets.
- Execution writes `Pending` before transport. A 2xx response is `Succeeded`; a
  received non-2xx response is `Failed`; timeout or connection ambiguity is
  `Unknown`. No terminal result retries automatically.
- Certificate verification is required. Lana source cannot supply an absolute
  destination, authorization header, credential, or TLS-verification override.

## Rationale

The record envelope keeps transport failure distinct from a domain outcome.
The capability fixes the destination before policy evaluation, so policy cannot
accidentally widen network authority. A single webhook action is enough to prove
the authorization/receipt boundary before adding connectors.

## Compatibility

Existing `std/http` behavior is unchanged. Legacy planned-effect names may
remain compatibility aliases, but cannot acquire execution authority. Old LABC
chunks remain executable. New record consumers negotiate schema and ABI
versions explicitly.

## Test coverage

- Record round trips preserve unresolved, failed, claim, decision, and receipt
  fields.
- Installed C consumer checks ABI version, ownership, and malformed records.
- Trusted local HTTPS tests cover success, non-2xx, rejected authority, revoked
  capability, digest mismatch, timeout-to-unknown, no retry, and no secret
  leakage.
