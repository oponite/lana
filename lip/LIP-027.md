# LIP-027: Mixed-precision tensor dtypes (fp32 / fp16 / bf16)

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-07

## Motivation

LIP-004 defines a tensor's numeric dtype as `number` (IEEE 754 binary64) or
`complex` (a pair of binary64). The backend is binary64-only: `cblas_dgemm` /
`cblas_zgemm` on macOS (`vm/rust/lana-vm/src/backend.rs`, `vm/c/backend.c`),
with a single float32 Metal `sgemm` as the only non-binary64 path
(`vm/rust/lana-vm/src/metal.rs`).

Training (LIP-006) does not need binary64. The standard practice in PyTorch and
JAX is mixed precision: weights and activations in fp32, matmul in fp16 or bf16
with fp32 accumulation. That is a 2–4× speedup on CPU and the difference
between usable and not on GPU. Lana has no way to express it: every tensor is
binary64, so a training run pays double the memory traffic and double the FLOP
cost for precision it never uses.

This LIP makes lower precision a **first-class, explicit choice** — not a
silent downcast. It is the precision half of the training-speed work; the
fused-step implementation is tracked separately in `mLIP-001.md`.

## Specification

### 1. Dtype values

A tensor's dtype is a first-class property alongside `is_complex`. The dtype
set is:

| dtype | element | bytes/element | backend |
|---|---|---|---|
| `"f64"` | binary64 | 8 | `dgemm` / `zgemm` (current) |
| `"f32"` | binary32 | 4 | `sgemm` (Accelerate) |
| `"f16"` | binary16 | 2 | native loop / Metal |
| `"bf16"` | bfloat16 | 2 | native loop / Metal |
| `"complex"` | pair of binary64 | 16 | `zgemm` (current) |

- `"f64"` and `"complex"` are the existing dtypes, unchanged. `"complex"` is
  binary64 complex; there is no low-precision complex in this LIP.
- The `state` dtype of LIP-007 is binary64 complex and is out of scope here.
- A tensor's buffer is contiguous and row-major exactly as in LIP-004; only
  the element width changes. `offset` and `strides` are in elements, so views
  are dtype-agnostic.

### 2. Construction

Constructors take an optional `dtype:` named parameter, defaulting to `"f64"`
so every existing program is unchanged:

```lana
let a = tensor([1.0, 2.0, 3.0], dtype: "f32");
let b = zeros([2, 3], dtype: "f16");
let c = ones([2, 2], dtype: "bf16");
let d = eye(3);                    // still "f64"
```

- `tensor(...)` with a `dtype:` of `"f16"`/`"bf16"` accepts number literals and
  rounds them to the target precision at construction, using IEEE
  round-to-nearest-even.
- `dtype(t)` returns the dtype string. `ndim(t)` and `shape(t)` are unchanged.
- `tensor_complex` (LIP-004) and `state_tensor` (LIP-007) do not take a
  `dtype:` — they are `"complex"` and `state` respectively.

### 3. Cast

`cast(t, dtype)` converts a tensor to another dtype. It is the explicit escape
hatch and the only way to change dtype:

```lana
let w = cast(weights, "f16");   // downcast, explicit
let x = cast(w, "f64");         // upcast for exact inspection
```

- `cast` to the same dtype is a no-op (returns the same tensor).
- `cast` materializes a new tensor; it never mutates a view or its base buffer.
- `cast` between `"f64"` and `"complex"` is out of scope (complex is a separate
  value kind in LIP-004); `cast` operates within the real dtypes.
- `cast` never raises on precision loss — precision loss is the point. The
  result is approximate by construction and its provenance records the dtype.

### 4. Arithmetic

- **Element-wise** (`+ - * /`) requires both operands to have the **same**
  dtype; a mismatch raises `LANA_ERR_TYPE`. Use `cast` to align explicitly.
  There is no silent promotion. A scalar literal in an element-wise op adopts
  the tensor's dtype (cast to it), so `f16_tensor + 1.0` is `"f16"` — the
  PyTorch behavior.
- **matmul** accepts mixed dtypes. The output dtype defaults to the input
  dtype when both inputs match, and to the higher precision for a
  `"f64"`/`"f32"` mix. An optional `out_dtype:` named parameter overrides the
  output dtype explicitly — the knob for keeping the loss/gradient in fp32:
  `matmul(a, b, out_dtype: "f32")`. For `"f16"`/`"bf16"` inputs the internal
  accumulation is always fp32 regardless of the output dtype.
- **Reductions** (`sum`/`mean`/`max`/`min`): a full reduction returns a
  `number` (binary64), matching LIP-004, regardless of input dtype; `sum`/
  `mean` accumulate in fp32 for `"f16"`/`"bf16"` inputs. An axis reduction
  returns a tensor and preserves the input dtype. The non-finite rejection and
  complex-typing rules of LIP-004 are unchanged.
- **f16 overflow.** `"f16"` has a narrow range (max ≈ 65504); a value that is
  finite in `"f64"` can overflow to `inf` in `"f16"`. This is expected and
  approximate, not an error — the result is approximate by construction.
  `"bf16"` shares fp32's range, so it does not overflow where fp32 does not.
- **Training (LIP-006).** `train` inherits the dtype of its tensors; there is
  no separate compute-dtype knob in this LIP. A user chooses precision by
  constructing `initial_params` at the desired dtype.

### 5. Backend

- `"f32"` matmul lowers to `cblas_sgemm` on macOS (Accelerate) and the portable
  loop elsewhere, through the same dispatch point as LIP-004 so C/Rust
  differential byte identity holds.
- `"f16"`/`"bf16"` have no standard CPU BLAS entry point. On CPU they lower to
  native loops (fp32 accumulation) through the same dispatch point; on a GPU
  backend they lower to Metal kernels. A build without a GPU uses the native
  loop. The CPU speedup is memory-bound (half the bytes), not guaranteed
  compute-bound; acceptance requires a measurement on a representative
  training workload before this path is relied on.
- No binary64 input is silently downcast: a lower dtype is only reached by an
  explicit `dtype:` at construction or an explicit `cast`.
- Provenance records the dtype and precision of every tensor operation, so an
  approximate result is never mistaken for an exact one.

### 6. Errors

| Condition | Error |
|---|---|
| unknown `dtype:` value | `LANA_ERR_INVALID_PARAMETERS` |
| element-wise op on mismatched dtypes | `LANA_ERR_TYPE` |
| `cast` to/from `"complex"` | `LANA_ERR_TYPE` |
| `dtype:` on a non-tensor constructor | `LANA_ERR_TYPE` |
| `dtype(t)` on a non-tensor | `LANA_ERR_TYPE` |

## Rationale

- **Explicit, not silent.** LIP-004's "binary64 CPU inputs are never silently
  downcast" is preserved: lower precision is only ever chosen by the
  programmer. This also aligns with the relaxed GPU-precision requirements in
  `REMAINING_WORK.md` (explicit approximate precision and tolerances allowed).
- **Match PyTorch/JAX.** LIP-004's stated goal is to match, not beat, the
  numeric stacks. Mixed precision with fp32 accumulation is the industry
  convention, so the surface mirrors it.
- **No promotion.** Silent promotion would make precision loss invisible and
  break the "explicit" contract. Requiring same-dtype element-wise ops and an
  explicit `cast` keeps precision a visible, deliberate choice.
- **fp16/bf16 on CPU are native loops, not BLAS.** There is no portable
  half-precision CBLAS; a native loop with fp32 accumulation is correct and
  can be faster than binary64 for memory-bound work. The speedup is not
  guaranteed and must be measured before the path is relied on. GPU is where
  the real speedup lands, and the dispatch point leaves that open.

## Design test

1. **Can a programmer guess what this does?** Yes — `dtype: "f32"` and
   `cast(t, "f16")` are self-explanatory.
2. **Does this resemble an existing concept?** Yes — dtype is the standard
   concept in NumPy/PyTorch/JAX.
3. **New terminology unnecessarily?** No — `dtype`, `fp32`, `fp16`, `bf16` are
   industry-standard.
4. **Simple case stays simple?** Yes — the default is `"f64"`; every existing
   program is unchanged.
5. **Advanced behavior discoverable later?** Yes — the `dtype:` parameter and
   `cast` are discoverable when a user needs them.
6. **Can the programmer inspect what Lana is doing?** Yes — `dtype(t)` returns
   the dtype and provenance records it.
7. **Escape to a concrete representation?** Yes — `cast(t, "f64")` recovers an
   exact value for inspection.
8. **Unusual behavior explicit?** Yes — lower precision is always explicit,
   never silent.
9. **Understandable at 11:30 PM?** Yes — dtype is a familiar, visible property
   of a tensor.
10. **More powerful without harder?** Yes — adds precision control without
    changing existing f64 behavior.

## Compatibility

- **New dtype values** on `VAL_TENSOR`; existing `"f64"`/`"complex"` tensors
  are unchanged.
- **No LABC format change** — tensor construction is a host call
  (`OP_HOST_CALL`), so the dtype is a host-call argument, not a bytecode
  change. Bytecode version stays `2`.
- **New host-call ID** `cast`; constructors gain a `dtype:` argument (no new
  construction host-call IDs).
- **Backend** gains `cblas_sgemm` for `"f32"` and native loops for
  `"f16"`/`"bf16"`; both VMs must select the same backend per platform so
  C/Rust differential byte identity holds.
- **Resource limits unchanged** (256 MiB, 50,000,000 instructions); a tensor's
  buffer and per-operation temporaries count against the memory limit using the
  actual element width (an `"f16"` buffer is a quarter of an `"f64"` buffer).
- **Replay** holds per `(seed, inputs, dtype, backend, version)`: the same
  inputs at a fixed dtype reproduce the same bytes. Cross-dtype identity is not
  claimed — fp16 is not bit-identical to fp64, and that is expected.

## Test coverage

- Construction with each `dtype:`; `dtype(t)` returns the dtype; default is
  `"f64"`.
- `cast` round-trips and precision loss; `cast` to the same dtype is a no-op;
  `cast` to/from `"complex"` raises.
- `"f32"` matmul against known results; `"f16"`/`"bf16"` matmul within
  tolerance with fp32 accumulation; `matmul(a, b, out_dtype: "f32")` returns
  the requested output dtype.
- Measurement: fp16/bf16 native-loop speedup on a representative training
  workload, recorded in `PERFORMANCE.md`, before the path is relied on.
- Element-wise op on mismatched dtypes raises; `cast`-aligned operands succeed;
  a scalar literal adopts the tensor's dtype.
- Full reductions return a `number` regardless of dtype; axis reductions
  preserve dtype; `sum`/`mean` accumulate fp32 for `"f16"`/`"bf16"`.
- f16 overflow: a value finite in f64 that exceeds f16 range becomes `inf`, not
  an error.
- Memory accounting: an `"f16"` buffer accounts a quarter of an `"f64"` buffer.
- Replay: same seed and dtype reproduce identical bytes.
- Differential conformance: byte-identical C11 vs Rust for `"f32"` (sgemm both
  sides) and for the `"f16"`/`"bf16"` native loops.
