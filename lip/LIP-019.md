# LIP-019: Networking and HTTP

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana has no networking. The only effectful host calls are four filesystem
operations and a hash. A huge fraction of Python's universality is web and
network work — HTTP clients, servers, and glue between services. A language
that cannot reach the network cannot participate in the systems that actually
make decisions under uncertainty (service health, forecasting, routing), which
is Lana's stated domain.

This LIP adds socket and HTTP host calls, gated by a `net` capability, returning
`Result<T, E>` so a network failure is a value, not a crash. A stdlib HTTP
client and server (LIP-016) layer over these primitives.

## Specification

### 1. Host calls

```lana
let resp = http_get(url, headers: {}, timeout_ms: 5000);
let resp = http_post(url, body, headers: {}, timeout_ms: 5000);
let sock = socket_connect(host, port);
let n    = socket_send(sock, bytes);
let data = socket_recv(sock, max_bytes);
socket_close(sock);
```

- `http_get` and `http_post` return a `Result<HttpResponse, E>` where
  `HttpResponse` carries `status`, `headers` (a map), and `body` (a string).
- `socket_connect` returns a `Result<Socket, E>`; `socket_send` and
  `socket_recv` return `Result<number, E>` and `Result<string, E>`.
- Every call takes an explicit `timeout_ms`; the default is bounded (5000 ms).
  A timeout is a `Result` error, not a hang.

### 2. Effects and capability

- All network calls are `io` effects and require a `capability("net")` grant.
  Without it, the call fails before any socket is opened.
- Network calls cannot run inside an unresolved branch (consistent with the
  existing host-call rule).

### 3. TLS

- `https` is supported through a bundled TLS backend. Certificate verification
  is **on by default**; disabling it requires an explicit, named option
  (`verify: false`), never a silent default.
- A failed verification is a `Result` error carrying the reason.

### 4. Determinism and provenance

- A network response is an `Information` value rooted at the request: the
  provenance records the URL, the request time, and the response identity, so
  a decision that consumed a network reading can be audited and replayed
  against the recorded response.
- Network I/O is inherently non-deterministic; Lana does not pretend otherwise.
  The `Information` root is the boundary where non-determinism enters, and
  everything downstream of it is pure.

### 5. stdlib layer

- `std/http` provides `client.get`, `client.post`, and a minimal `server`
  built on the host calls. The stdlib layer is pure Lana over the host calls
  and adds no new semantics.

## Rationale

- **`Result`, not exceptions.** A network call fails constantly (DNS, timeout,
  TLS, connection refused). Returning `Result<T, E>` keeps the
  no-partial-result contract and forces the caller to handle failure.
- **Capability-gated.** Network access is a consequential, outward-facing
  action; it should require an explicit grant, matching LIP-012 and
  secure-by-default.
- **TLS on by default.** Insecure-by-default is how Python's `requests` got
  `verify=False` footguns. Lana inverts it.

## Compatibility

- **New host calls** appended to `LanaHostCallId` (C and Rust must match).
- **No LABC change** — networking is host calls, not opcodes.
- **New capability** `"net"`.
- **New native dependency** (a TLS backend) for the C11 and Rust VMs.
- **Resource limits unchanged.**

## Test coverage

- `http_get`/`http_post` against a local test server: status, headers, body.
- Timeout: a slow endpoint returns a timeout `Result`, not a hang.
- TLS: a self-signed certificate fails verification by default and succeeds
  with `verify: false`.
- Capability denial: a network call without `capability("net")` fails before
  any socket is opened.
- Provenance: a response's `Information` root records the URL and request time.
