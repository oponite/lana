# LIP-012: Compute, data, and weights as capabilities

- **Status:** Draft (capability `grant`/`revoke` machinery implemented; GPU/data/weights gating deferred)
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Python's model just calls `.cuda()` and reads files. There is no permission
boundary: a model can silently spend GPU compute or read training data, and
nothing records *what it touched or who let it*. Security is a convention the
programmer opts into, not a property the language enforces.

Lana already has the primitives this needs: `capability(name)` creates a named
token, `planned_effect(kind, capability)` is an inert typed plan, and
`execute_effect` runs it once and caches a receipt by `(plan identity, committed
revision)` (`spec/SPEC.md` "Effects and capabilities"). This LIP makes the three
resources a model actually consumes — **compute** (the GPU backend), **data**
(training inputs), and **weights** (the trained model) — capabilities with
explicit grant/revoke. A model cannot read data or spend compute without an
auditable, revocable effect.

This is the "secure by default / human in the loop" differentiator: the default
is no access, and every grant is an explicit, recorded act.

## Specification

### 1. Capability kinds

```lana
let gpu     = capability("gpu");
let data    = capability("data");
let weights = capability("weights");
```

- `capability(name)` is the existing constructor; this LIP standardizes three
  names and their semantics:
  - `"gpu"` — authority to dispatch tensor operations to the GPU backend
    (LIP-004 §5).
  - `"data"` — authority to read a training dataset (LIP-006).
  - `"weights"` — authority to read or use a trained model's parameters.
- A capability is a first-class value (`VAL_SHARED_CAPABILITY`); it is inert
  until used by a planned effect. The constructor compiles to the existing
  `shared_information` host call (id 38), which returns an admin
  `LanaCapabilityToken`; there is no separate `capability` host call.

### 2. Grant and revoke

```lana
let token = grant(gpu, "use");   // a distinct, revocable token
revoke(token);                   // invalidates the token
```

- `grant(capability, "use"|"admin")` creates a distinct token; `"admin"` may
  further grant. `revoke(token)` invalidates it. This generalizes the existing
  `shared_grant`/`shared_revoke` pattern to capabilities.
- `grant` and `revoke` are two new host calls (`LANA_HOST_GRANT` = 74,
  `LANA_HOST_REVOKE` = 75). `grant` maps `"use"`→`READ` and `"admin"`→`ADMIN`
  and delegates to `lana_shared_capability_grant`; `revoke` is a single-argument
  invalidation (`lana_shared_capability_invalidate`), distinct from the
  two-argument `shared_revoke(admin, target)`.
- A grant is itself an auditable act: it records the granting task lineage and
  revision, so *who let it* is answerable.
- Revocation is immediate: a revoked token fails at the next `execute_effect`,
  not at some later checkpoint.

### 3. Capability-gated operations

The operations that consume these resources are planned effects requiring the
corresponding capability:

```lana
let plan = planned_effect("train", [data, gpu]);   // requires data + gpu
let result = execute_effect(plan);                 // auditable, revocable
```

- **Compute.** Dispatching a tensor operation to the GPU backend is a planned
  effect requiring a `"gpu"` capability. Without it, the operation runs on the
  CPU backend (LIP-004 §5) or is rejected — never silently escalated.
- **Data.** `train` (LIP-006) reading a dataset is a planned effect requiring a
  `"data"` capability. A model cannot read data it was not granted.
- **Weights.** Reading or using a trained model's parameters is a planned effect
  requiring a `"weights"` capability. The trained result (LIP-006) is inert
  until the capability is granted.
- The effect receipt (`effect_status`) records the plan identity, the committed
  revision, and the capabilities consumed, so *what did this model touch* is a
  first-class question.

### 4. Audit and replay

- Every compute/data/weight access is a planned effect with a receipt; the
  receipt is a value with provenance, so the access is auditable and replayable
  like any other Lana value.
- The grant and the access are both recorded: the audit trail answers *what was
  touched* (the effect) and *who let it* (the grant).
- Deterministic replay (§9.7.5) covers the effect: the same
  `(seed, inputs, version)` reproduces the same receipt bytes.

### 5. Errors

| Condition | Error |
|---|---|
| `execute_effect` without the required capability | `LANA_ERR_CAPABILITY` |
| `execute_effect` with a revoked token | `LANA_ERR_CLAIM_REVOKED` |
| `grant`/`revoke` on a non-capability value | `LANA_ERR_TYPE` |
| unknown capability name | `LANA_ERR_INVALID_PARAMETERS` |
| `planned_effect` with a non-capability argument | `LANA_ERR_TYPE` |

## Rationale

- **Secure by default.** The default is no access: a model cannot read data or
  spend compute unless a capability is explicitly granted. Python's `.cuda()`
  and file reads have no such boundary; Lana's is enforced by the language.
- **Human in the loop.** Grant and revoke are explicit, recorded acts. The human
  decides what a model may touch, and can revoke it at any time — the
  "consequential or irreversible action needs a human to confirm" principle made
  structural.
- **Inherited, not invented.** `capability`, `planned_effect`, `execute_effect`,
  and `effect_status` already exist; this LIP names three capability kinds and
  gates the tensor/training operations behind them. No new permission system is
  built — the existing effect discipline is applied to the resources a model
  actually consumes.
- **Auditable by construction.** Because the access is a planned effect with a
  receipt, "what did this model touch, and who let it" is answered by the same
  provenance machinery as every other Lana value.

## Compatibility

- **No new `ValueType` tag** — capabilities are `VAL_SHARED_CAPABILITY`, planned
  effects are `LanaPlannedEffect` (both existing).
- **No LABC format change** — `grant`/`revoke` are host calls; the gating is on
  existing operations. The bytecode version stays `2`.
- **New host-call IDs** `grant`, `revoke` appended to `LanaHostCallId` (C and
  Rust must match).
- **Depends on LIP-004** (tensor + GPU backend) and **LIP-006** (training), and
  the existing capability/planned-effect/effect-status machinery.
- **Resource limits unchanged**; effect receipts count against the 256 MiB
  limit.

## Test coverage

- A tensor op without a `"gpu"` capability runs on the CPU backend; with it,
  dispatches to the GPU backend.
- `train` without a `"data"` capability is rejected; with it, succeeds.
- Reading weights without a `"weights"` capability is rejected; with it,
  succeeds.
- `revoke` invalidates a token: the next `execute_effect` fails with
  `LANA_ERR_CLAIM_REVOKED`.
- Audit: the effect receipt records the capabilities consumed; the grant
  records the granting task lineage.
- Replay: the same `(seed, inputs, version)` reproduces byte-identical receipts.
- Errors: missing capability, revoked token, unknown capability name.
- Differential conformance: byte-identical C11 vs Rust output for a fixed seed.
