# LIP-003: LABC v2 as the emitted bytecode format

- **Status:** Draft
- **Author:** —
- **Date:** 2026-09-04

## Motivation

The compiler and its bootstrap artifact emit LABC v2 (`LABC_VERSION == 2` in
`vm/include/bytecode.h`), and the dual-version loader accepts both v1 and v2
chunks. The authority documents still describe LABC v1 as the only emitted
format: `spec/BYTECODE.md` states "the assembler emits LABC v1 only",
`spec/SPEC.md` lowers Information forms "to LABC v1", and
`papers/semantics.md` §7.6 names LABC v1 as the single encoding. The
implementation and the authority order have diverged.

## Specification

- `spec/BYTECODE.md` describes LABC v2 as the emitted format: the version field
  is `2`, the assembler emits v2, and the loader accepts both v1 and v2 chunks.
- `spec/SPEC.md` lowers source-level Information forms to LABC v2.
- `papers/semantics.md` §7.6 records that the encoding boundary is LABC v2, with
  the dual-version loader accepting v1 and v2.
- No opcode, register, or resource-limit change. The change is a documentation
  correction that brings the authority documents in line with the already-shipped
  implementation.

## Rationale

The compiler has emitted v2 since the LABC v2 work landed; the loader already
accepts both versions. The authority documents are the highest source of truth
and must not describe a format the toolchain no longer produces. Correcting them
removes a false statement ("emits LABC v1 only") without altering any behavior.

## Compatibility

The dual-version loader continues to accept LABC v1 and v2 chunks. No bytecode,
VM, or resource-limit change. Existing v1 chunks remain loadable; new chunks are
v2.

## Test coverage

- The differential conformance suite already asserts byte-identical C11/Rust
  behavior for v2 chunks.
- The loader's dual-version acceptance is covered by existing verifier and
  loader tests that accept both `LABC_VERSION` and `LABC_VERSION_1`.
- No new runtime tests are required; this LIP changes documentation only.
