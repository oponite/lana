# LIP-018: Two-way foreign function interface

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

The native bridge is one-way: Python (or C) loads Lana and drives it. Lana
cannot call out to an existing C, Rust, or Python library. Python's
universality is "glue to anything" — ctypes, cffi, and pybind11 are how it
absorbs every other ecosystem without reimplementing it. A language that can
only be called, and cannot call, is an island.

This LIP adds a two-way FFI: Lana declares a foreign signature, loads a shared
library, and calls it. The call is an `external_call` effect, gated by a
capability, and a crash in the foreign code is contained and reported rather
than taking down the VM. This is the move that lets Lana eat every other
ecosystem instead of only its own.

## Specification

### 1. Declaration

```lana
let add = ffi_declare("int add(int, int)");
let lib = ffi_load("libmath.so");
let result = ffi_call(lib, add, [2, 3]);
```

- `ffi_declare(signature)` parses a C-style signature and returns a typed
  callable descriptor. The signature is a literal string; unknown types are a
  compile-time error.
- `ffi_load(path)` loads a shared library and returns a library handle.
- `ffi_call(lib, fn, args)` invokes the function and returns a `Result<T, E>`.

### 2. Type mapping

| Lana type | C type |
|---|---|
| `number` | `double` or `int` (per signature) |
| `string` | `const char *` (UTF-8, NUL-terminated) |
| `array` | pointer + length (a `struct { T *data; size_t len; }`) |
| `map` | not marshallable by default |
| `STATE`, `STATE_DIST`, `Information` | not marshallable by default |

- `STATE`, `STATE_DIST`, and `Information` are not marshallable across the FFI
  boundary in the initial release; passing one raises `LANA_ERR_TYPE`. This
  keeps the probabilistic semantics inside Lana rather than leaking them into
  an untyped ABI.

### 3. Effects and capability

- An FFI call is an `external_call` effect. It requires a
  `capability("ffi")` grant; without it, the call fails before loading or
  invoking anything.
- `ffi_load` and `ffi_call` are effectful and cannot run inside an unresolved
  branch (consistent with the existing rule that host calls fail before
  producing an effect in a guarded environment).

### 4. Safety and containment

- A crash (signal) in the foreign library is contained: the VM reports
  `LANA_ERR_EXTERNAL` with the library and function identity, and the task
  fails without corrupting the VM heap.
- The FFI is **unsafe by default**: it is the programmer's responsibility to
  declare the signature correctly. Lana does not verify the ABI at runtime
  beyond the declared types.

### 5. Reverse direction

- The existing native bridge (Python loads Lana) is unchanged. This LIP adds
  the forward direction (Lana loads C/Rust). A Lana→Python direction reuses
  the existing Python bridge in reverse and is a follow-on, not part of this
  LIP.

## Rationale

- **Capability-gated, not ambient.** Calling arbitrary native code is the
  highest-risk operation a language can perform. Gating it behind an explicit
  `ffi` capability matches Lana's secure-by-default stance and LIP-012's
  resource-as-capability model.
- **`Result`, not exceptions.** A foreign call can fail for many reasons
  (missing symbol, bad argument, crash). Returning `Result<T, E>` keeps the
  no-partial-result contract.
- **Keep probabilistic values inside Lana.** Marshalling `STATE` across an
  untyped ABI would silently discard its semantics. Refusing it is the honest
  default.

## Compatibility

- **New host calls** `ffi_declare`, `ffi_load`, `ffi_call` appended to
  `LanaHostCallId` (C and Rust must match).
- **No LABC change** — FFI is host calls, not opcodes.
- **New effect surface** documented under `external_call`.
- **New capability** `"ffi"`.
- **Resource limits unchanged.**

## Test coverage

- Call a known C function (e.g. `add`) and verify the result.
- Type marshalling: `number`→`int`, `number`→`double`, `string`, `array`.
- Capability denial: an FFI call without `capability("ffi")` fails before load.
- Crash containment: a foreign function that raises a signal is reported as
  `LANA_ERR_EXTERNAL` and the VM survives.
- `STATE`/`STATE_DIST` marshalling is rejected with `LANA_ERR_TYPE`.
