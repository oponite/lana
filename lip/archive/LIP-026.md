# LIP-026: Language design requirements

- **Status:** Final
- **Author:** Vijay
- **Date:** 2026-09-06

## Motivation

Lana's deep machinery — `STATE`, provenance DAGs, deferred operations, density
matrices, evidence — is real and growing (LIPs 004–016, 018–025). The risk is
not that it exists; it is that it leaks into the surface and makes ordinary
code harder to read than a Python or Ruby equivalent. `spec/SPEC.md` states
*what* the surface is; nothing states the *shape* the surface must keep.

This LIP adopts a written design charter: fifteen design requirements plus a
core principle and a ten-question design test. It gives reviewers, the BDFL,
and future LIP authors a shared, citable standard for "does this feel like
Lana" that today only exists as an unwritten assumption.

## Specification

### 1. Normative adoption

The following requirements are adopted as normative constraints on Lana's
source surface and programmer-visible runtime behavior. "MUST" is binding;
"SHOULD" is a strong default that requires written justification to deviate.

**R1 — Familiar by default.** Lana MUST feel familiar to programmers coming
from Python, Ruby, JavaScript, or similar. Ordinary deterministic code MUST use
conventional concepts: variables, functions, conditionals, loops, arrays, maps,
modules, return values. Lana-specific concepts MUST NOT be required for
ordinary programming.

**R2 — Progressive disclosure.** Advanced semantics MUST be opt-in. Simple use
cases expose simple syntax. `STATE` MUST keep a simple beginner-facing API while
preserving full access to its underlying representation.

**R3 — Conventional terminology.** Lana MUST reuse established programming
terminology where the concept already exists (`array`, `map`, `matrix`,
`dataset`, `function`, `module`, `filter`, `group`, `join`, `sample`, `trace`).
Lana MUST NOT invent new terminology solely because the implementation differs.

**R4 — Human-readable operations.** Core operations SHOULD read as programmer
intent: `measure state`, `filter users`, `group orders by customer`,
`join orders with customers`, `sample distribution`. Formal mathematical terms
MAY exist in advanced APIs but MUST NOT be required for common operations.

**R5 — Ordinary code stays ordinary.** Functions MUST behave like functions;
control flow MUST remain conventional; deterministic values MUST behave like
deterministic values. `STATE`, evidence, provenance, laziness, and probability
MUST NOT be forced into code that does not need them.

**R6 — Novelty by opt-in.** Lana-specific behavior MUST appear only where the
programmer explicitly uses a Lana-specific feature. "Familiar by default,
novel by opt-in." The language MUST be learnable incrementally.

**R7 — Unusual behavior is inspectable.** Lazy values MUST expose whether they
are evaluated; deferred operations SHOULD expose their execution plan;
unresolved values SHOULD expose status and representation. Suggested
interfaces: `value.status`, `value.inspect`, `value.explain`.

**R8 — Concrete escape hatches.** Every high-level abstraction MUST expose its
concrete operational representation: `state.inspect` / `state.measure` /
`state.to_matrix`; `dataset.plan` / `dataset.materialize` / `dataset.size`;
`value.evidence` / `value.origin` / `value.explain`. Abstractions MUST NOT be
opaque black boxes.

**R9 — First-class explainability.** A runtime value MUST be able to answer:
what it is, its type, where it came from, what produced it, whether it is
evaluated, whether it is unresolved, its dependencies, and what evaluation or
measurement will do. This is a runtime capability, not a debugging feature.

**R10 — Concrete error messages.** Errors MUST identify the offending value,
its type, the expected type/operation, why the operation failed, and an obvious
correction when one exists. Example failures MUST read like prose with a
suggested fix, not a status code.

**R11 — Syntax optimizes for humans.** When syntax elegance conflicts with
usability, usability wins: readability, discoverability, tired-user usability,
predictable behavior, low cognitive overhead, easy debugging, minimal
punctuation, semantic clarity. Formal semantics determine behavior, not surface
syntax.

**R12 — No implementation leakage without benefit.** Laziness, density
matrices, provenance DAGs, bytecode, VM representation, and storage or
vectorization MUST NOT leak into ordinary source. Implementation details become
visible only when they help the programmer reason about or control execution
(e.g. `users = load("users.csv")`, not
`users = deferred_lazy_dataset_relation("users.csv")`).

**R13 — STATE is a type, not a language.** `STATE` MUST integrate with the
normal type system. Basic use MUST NOT require understanding density matrices;
advanced users retain the full mathematical representation. The beginner
concept is "a value that can remain unresolved until a concrete result is
required."

**R14 — Depth without mandatory complexity.** The same value MUST support all
levels:

```lana
x = state(0.7)
result = measure(x)        # beginner
x.status                   # intermediate
x.to_matrix                # advanced
```

**R15 — Design test.** Every new feature or surface change MUST be evaluated
against the ten-question design test in §3 and the result recorded.

### 2. Core design principle

> Simple things MUST look simple. Deep things MUST remain possible.

Equivalently: *familiar by default, novel by opt-in, transparent when doing
anything unusual.*

### 3. Design test

Every LIP and language-feature proposal MUST answer the following, recording a
yes/no plus one-line justification for each:

1. Can a programmer guess what this does?
2. Does this resemble an existing programming concept where appropriate?
3. Are we introducing new terminology unnecessarily?
4. Can the simple case remain simple?
5. Can advanced behavior be discovered later?
6. Can the programmer inspect what Lana is doing?
7. Can the programmer escape to a concrete representation?
8. Is unusual behavior explicit?
9. Would this still be understandable when debugging at 11:30 PM?
10. Does this feature make Lana more powerful without making unrelated code
    harder to understand?

A "no" requires written justification in the LIP; a design test section is
required in the same way the template requires Compatibility.

### 4. Authority placement

The design requirements sit between the mathematical papers and the surface
spec: `papers/semantics*.md` define the mathematics, this charter defines the
shape of the source surface, and `spec/SPEC.md` defines the concrete surface
and runtime behavior. Any conflict between this charter and a proposed surface
change is resolved by amending one or the other through the normal LIP process.

### 5. Enactment

- `lip/README.md` lists this LIP as the design charter.
- `lip/TEMPLATE.md` gains a "Design test" section.
- This LIP makes no change to source syntax, bytecode, VM, or runtime math.

## Rationale

- **Written line between deep and simple.** The language has adopted deep
  semantics (provenance, density operators, deferred execution). Without a
  stated boundary, each feature negotiates the boundary alone and the surface
  drifts toward the most expressive, not the most usable, shape.
- **Adoption via LIP gives it a date and a status.** An unwritten philosophy
  cannot be cited; this can.
- **Low cost, high leverage.** The design test is ten yes/no questions. It
  cannot reject a technically sound feature, but it forces the author and the
  BDFL to decide consciously where novel semantics become visible.
- **Rejected alternative — fold into `spec/SPEC.md`.** The spec is an
  operational contract; mixing philosophy into it makes every conformance
  decision ambiguous. Keeping the charter separate preserves the spec's
  precision while making the philosophy citable.

## Compatibility

- **No change** to source syntax, LABC bytecode, VM behavior, resource limits,
  or the mathematical objects in `papers/semantics*.md`.
- Existing accepted LIPs and `spec/SPEC.md` are presumed conformant. If a
  conformance review finds a violation, it is filed as a follow-up amendment,
  never silently changed.
- Policy documents only: no runtime, performance, or packaging impact.

## Test coverage

- Policy change: the enforcement mechanism is the design test applied to each
  future LIP.
- A one-time conformance review of `spec/SPEC.md` against the fifteen
  requirements, recorded as an appendix to this LIP, flags any existing surface
  that violates the charter.
- The canonical example patterns in R4, R7, R8, R10, and R14 are matched against
  existing spec examples and corrected where they diverge.

## Conformance review

Reviewed against `spec/SPEC.md` on 2026-09-07.

| Requirement | Result | Evidence or follow-up |
|---|---|---|
| R1–R6 | Conforming | Ordinary control flow remains conventional; STATE, uncertainty, and effects are explicit. |
| R7 | Conforming | Information inspection, dataset plans, and debugger commands expose unusual behavior. |
| R8 | Conforming | State tensors, dataset plans/materialization, model records, and derivations expose concrete representations. |
| R9 | Partial | Information values are explainable; ordinary values do not yet expose one universal explain operation. |
| R10 | Partial | Source diagnostics are concrete; some VM host-call failures still surface stable error categories without a suggested correction. |
| R11–R13 | Conforming | Syntax stays human-oriented, implementation machinery stays below the surface, and STATE participates in normal expressions and types. |
| R14 | Partial | Beginner and advanced operations exist as functions and inspection commands rather than the illustrative property syntax in this LIP. |
| R15 | Conforming | The LIP template requires the ten-question design test. |

The partial findings are documented compatibility constraints, not permission
to invent new syntax. Any remediation requires its own authority-first change.
