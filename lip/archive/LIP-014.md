# LIP-014: Whole-run reproducibility and resumability

- **Status:** Final
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Python's reproducibility is a constant fight: nondeterminism, seed bugs, and
hardware drift mean the same code and data do not reliably produce the same
model. And a training run is not resumable — you restart from scratch or load a
checkpoint that captures only the parameters, not the optimizer state or the
step history, so the continuation is not the same run.

`spec/EVIDENCE.md` §5 already guarantees byte-identical replay for a
`(seed, inputs, version)`. This LIP extends that contract to the **entire
training run** — data, model, optimizer state, every step — as one replayable
derivation. You can resume from any step, reproduce any result exactly, and
audit why a weight is what it is.

## Specification

### 1. The run as one derivation

A training run (LIP-006 `VAL_TRAINING_RESULT`) is a single derivation node:

- Its inputs are the data, the model, the optimizer, and the seed.
- Its output is the final parameters, the step history, and the optimizer state.
- The whole run is one replayable derivation: the same `(seed, inputs, version)`
  reproduces the same output bytes, including every intermediate step.

### 2. Optimizer state as a first-class value

- The optimizer's internal state — Adam's `m`/`v`, SGD's momentum — is part of
  the run, not a hidden side effect. It is a value with provenance, carried
  alongside the parameters.
- The optimizer state is replayable: it is a function of the same
  `(seed, inputs, version)`, so a resumed run continues from the exact state the
  original run was in at that step.

### 3. Resume from any step

```lana
let run     = train(model, data, loss, adam(learning_rate: 0.001), initial_params, epochs: 10);
let step5   = run.steps[5];      // addressable step (a value)
let resumed = resume(run, 5);    // continue from step 5
```

- The step history is a value, so any step is an addressable resumption point.
- `resume(run, i)` returns a new run that continues from step `i` with the
  parameters and optimizer state the original run had at that step. The
  continuation is byte-identical to the original run's steps `i+1..`.
- `resume` is immutable: the original run is unchanged; the resumed run is a new
  value whose derivation records the resumption point.

### 4. Reproduce any result exactly

- The `(seed, inputs, version)` contract of `EVIDENCE.md` §5 extends to the
  whole run: fixed evaluation order, IEEE 754 binary64 with no fused-multiply-add
  reordering, the seeded PCG32 stream, and deterministic iteration order.
- A resumed run reproduces the original continuation exactly: `resume(run, i)`
  followed by the same steps yields byte-identical parameters to `run`'s final
  result.
- A version change may change bytes; a seed or input change may change bytes;
  nothing else may.

### 5. Audit why a weight is what it is

- The whole-run derivation records, for every weight, the exact sequence of
  steps — batch → gradient → update — that produced it (LIP-006 §4), now
  composed into one run-level provenance path.
- You can ask *why is this weight this value* and get the full chain: which
  batches, which gradients, which optimizer updates, in which order.

### 6. Errors

| Condition | Error |
|---|---|
| `resume` on a non-training-result value | `LANA_ERR_TYPE` |
| `resume` step index out of range | `LANA_ERR_KEY` |
| `resume` step index not a nonnegative integer | `LANA_ERR_INVALID_PARAMETERS` |
| non-finite optimizer state after a step | `LANA_ERR_INVALID_PARAMETERS` |

## Rationale

- **Structural, not a fight.** Python's reproducibility is a property the
  programmer must maintain by hand. Lana's is the existing replay contract
  (`EVIDENCE.md` §5) applied to the training run — the run is a value, so it is
  replayable by construction.
- **Resume is a value, not a checkpoint file.** Python's checkpoint captures
  parameters only; Lana's step history is a value that carries parameters,
  optimizer state, and provenance, so resuming is addressing a step, not
  reconstructing state from a partial snapshot.
- **Inherited, not invented.** The step history, provenance, and deterministic
  replay already exist (LIP-006, `EVIDENCE.md`); this LIP composes them into a
  single run-level derivation and adds `resume`.

## Compatibility

- **No new `ValueType` tag** — the run is the existing `VAL_TRAINING_RESULT`,
  extended to carry optimizer state; `resume` returns the same type.
- **No LABC format change** — `resume` is a host call; the step history is
  already a value. The bytecode version stays `2`.
- **New host-call ID** `resume` appended to `LanaHostCallId` (C and Rust must
  match).
- **Depends on LIP-006** (training primitive) and **LIP-010** (incremental
  learning — resume is the batch counterpart of incremental `observe`), and the
  replay contract of `EVIDENCE.md` §5.
- **Resource limits unchanged**; the step history and optimizer state count
  against the 256 MiB limit.

## Test coverage

- Two runs with the same `(seed, inputs, version)` produce byte-identical
  parameters, step history, and optimizer state.
- `resume(run, i)` continues byte-identically to the original run's steps
  `i+1..`.
- The optimizer state is a value: it is inspectable and replayable.
- Provenance: a weight's derivation traces the full batch → gradient → update
  chain.
- Errors: `resume` on a non-run value, out-of-range step index, non-integer
  step index.
- Differential conformance: byte-identical C11 vs Rust output for a fixed seed.
