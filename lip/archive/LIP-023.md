# LIP-023: Native JSON and data interchange

- **Status:** Final
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

JSON is only reachable through the Python bridge. A Lana program that needs to
read a config, consume an API response, or emit a decision record must round-trip
through Python. JSON is the universal data interchange format — the substrate
of every API, config file, and log. A language that cannot parse and emit it
natively cannot be the glue that a universal language must be.

This LIP adds native JSON parse and stringify, plus CSV and TOML, as a stdlib
module (LIP-016) over host calls. Parsing returns `Result<T, E>`; stringify is
deterministic. Parsed values carry provenance rooted at the source text.

## Specification

### 1. `std/json`

```lana
let parsed = json_parse(text);        // Result<Value, E>
let text   = json_stringify(value);   // string
```

- `json_parse` returns `Result<Value, E>`: `Ok(value)` on valid JSON, an error
  carrying the byte offset and reason on invalid JSON. It never returns a
  partial value.
- `json_stringify` is deterministic: object keys are emitted in a stable,
  specified order (sorted by key), so the same value always produces the same
  text.

### 2. Value mapping

| JSON | Lana |
|---|---|
| object | `map` |
| array | `array` |
| string | `string` |
| number | `number` (binary64) |
| `true` / `false` | `bool` |
| `null` | `null` |

- Duplicate object keys: the last occurrence wins, and the parse is accepted
  (specified, not an error).
- Trailing garbage after a complete value is rejected.

### 3. Number fidelity

- JSON numbers are parsed as binary64. An integer whose magnitude exceeds
  `2^53` is preserved as a string rather than silently rounded, so a large
  identifier is not corrupted. `json_stringify` emits such strings as JSON
  strings.

### 4. Provenance

- A parsed value is an `Information` value rooted at the source text: the
  provenance records the text identity, so a decision that consumed a parsed
  record can be audited and replayed against the exact input.

### 5. `std/csv` and `std/toml`

- `std/csv`: `csv_parse(text) -> Result<array<array<string>>, E>` and
  `csv_stringify(rows) -> string`, with a specified delimiter and quoting rule.
- `std/toml`: `toml_parse(text) -> Result<map, E>` and
  `toml_stringify(map) -> string`, matching the schema-1 `lana.toml` dialect.

## Rationale

- **`Result`, not exceptions.** Malformed input is the common case, not the
  exception. Returning `Result<T, E>` keeps the no-partial-result contract.
- **Deterministic stringify.** A decision record that serializes differently
  on each run is not reproducible. Stable key order makes stringify a pure
  function of the value.
- **Preserve large integers.** Silently rounding a 64-bit identifier to a
  binary64 is a data-integrity bug. Preserving it as a string is the honest
  default.

## Compatibility

- **New host calls** for the JSON/CSV/TOML codecs appended to `LanaHostCallId`
  (C and Rust must match).
- **No LABC change** — data interchange is stdlib + host calls.
- **No language change.**
- **Resource limits unchanged.**

## Test coverage

- Round-trip: `json_stringify(json_parse(x))` is stable for representative
  values.
- Malformed input: truncated, trailing garbage, bad escape — each returns a
  `Result` error with an offset.
- Number fidelity: an integer beyond `2^53` is preserved as a string.
- Duplicate keys: last-wins is specified and tested.
- Provenance: a parsed value's `Information` root records the source text.
- CSV/TOML: parse/stringify round-trips and the `lana.toml` dialect.
