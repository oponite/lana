# LIP-021: Text processing — strings, regex, formatting, unicode

- **Status:** Final
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana has strings but no way to split, match, format, or normalize them. Most
Python programs are text munging — parsing logs, shaping data, building
messages — and Python's universality rests heavily on its text-processing
surface. A language that cannot process text cannot do the glue work that
makes a language universal.

This LIP adds a text-processing standard library: string helpers, a
deterministic regex engine, explicit formatting, and unicode normalization.
It is stdlib work over host calls (LIP-016), with one new host call for the
regex engine.

## Specification

### 1. `std/string`

```lana
let parts = split("a,b,c", ",");        // ["a", "b", "c"]
let joined = join(["a", "b"], "-");     // "a-b"
let t = trim("  x  ");                  // "x"
let b = starts_with("abc", "a");        // true
let r = replace("abc", "b", "x");       // "axc"
let u = to_upper("abc");                // "ABC"
let s = substring("abcdef", 1, 3);      // "bc"
```

- All functions are `pure`. Indices are code-point offsets, not byte offsets
  (see §4).

### 2. `std/regex`

```lana
let re = regex_compile("a+b");
let m = regex_match(re, "aaab");        // Result<Match, E>
let s = regex_search(re, "xaaaby");     // Result<Match, E>
let r = regex_replace(re, "aaab", "c"); // "c"
```

- The regex engine is **deterministic and linear-time** (RE2-style): no
  catastrophic backtracking. A pattern that would require exponential
  backtracking in a backtracking engine is matched in linear time or rejected
  at compile time.
- `regex_compile` returns a `Result<Regex, E>`; an invalid pattern is a
  `Result` error, not a crash.
- The engine is a host call (`regex_compile`, `regex_match`, `regex_search`,
  `regex_replace`) backed by a bundled engine; the stdlib wraps it.

### 3. Formatting

```lana
let s = format("value: {} ({})", 3.14, "ok");  // "value: 3.14 (ok)"
let n = format_number(3.14159, precision: 2);   // "3.14"
```

- `format` uses `{}` placeholders, filled left-to-right. It is explicit
  formatting, not string interpolation into source (no new syntax).
- `format_number` takes an explicit `precision`; the default is full binary64
  round-trip precision.

### 4. `std/unicode`

- `char_length(s)` returns the number of code points (not bytes).
- `normalize(s, "NFC" | "NFD" | "NFKC" | "NFKD")` returns the normalized form.
- `to_upper`/`to_lower` in `std/string` are full case folding, not ASCII-only.

## Rationale

- **Linear-time regex.** Catastrophic backtracking is a denial-of-service
  vector and a silent blowup. A deterministic engine matches Lana's "no hidden
  blowup" stance and its resource-limit philosophy.
- **Explicit formatting, not interpolation.** String interpolation is new
  syntax; `format(...)` is a function. This keeps the change stdlib-only and
  avoids a SYNTAX review.
- **Code-point indexing.** Byte indexing silently corrupts non-ASCII text.
  Code-point indexing is the honest default for a language that treats strings
  as text.

## Compatibility

- **New host calls** for the regex engine appended to `LanaHostCallId` (C and
  Rust must match).
- **No LABC change** — text processing is stdlib + host calls.
- **No language change.**
- **Resource limits unchanged.**

## Test coverage

- `std/string`: each function, including empty and boundary inputs.
- `std/regex`: match/search/replace; an invalid pattern returns a `Result`
  error; a pathological pattern (e.g. `(a+)+$` against a long non-match)
  completes in linear time.
- Formatting: placeholder count mismatch, precision, round-trip.
- Unicode: normalization vectors (NFC/NFD), code-point vs byte length, case
  folding of non-ASCII.
