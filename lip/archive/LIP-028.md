# LIP-028: Standard-library ML and resident Metal tensors

- **Status:** Final
- **Author:** Vijay
- **Date:** 2026-09-07

## Motivation

LIP-016 reserves standard-library modules but does not define machine-learning
operations. Existing tensor computation is CPU-resident except for
`gpu_matmul`, which copies each input and result for every call. Lana 2.1 needs
one uncertainty-aware ML surface and an explicit, bounded way to keep a
training workload on an Apple GPU.

## Specification

### 1. `std/ml`

`std/ml` implements these model families in Lana over tensor, autodiff,
training, dataset, and model operations:

- linear and ridge regression;
- binary and multiclass logistic regression;
- dense feed-forward neural networks;
- linear-Gaussian Kalman filtering and RTS smoothing;
- categorical and diagonal-Gaussian hidden Markov models;
- histogram gradient-boosted trees for regression and binary classification;
- Kou, exponential-Hawkes, and combined Kou-Hawkes jump diffusion.

The common entry points are:

```lana
fit(kind, tensors, options) -> Result<FitResult, MlError>
fit_dataset(kind, dataset, options) -> Result<FitResult, MlError>
predict(model, inputs, options) -> Result<Prediction, MlError>
predict_tensors(model, inputs, options)
    -> Result<[prediction_tensor, uncertainty_tensor], MlError>
```

Temporal models additionally expose `filter`, `smooth`, `decode`, and
`simulate`. Every successful operation returns prediction and uncertainty;
there is no prediction-only ML entry point. Result maps contain `schema: 1`.
Validation failures return `{code, message, field}` as the error value.

The rich entry points return CPU tensors. `predict_tensors` preserves the
model device. Provenance remains the normal derivation of the returned value;
the result records method, assumptions, model version, device, and precision
without duplicating the derivation graph.

Jump fitting accepts returns or explicit event times and sizes. Returns require
an explicit detection threshold, recorded in the fitted model. `mode` is one
of `"kou"`, `"hawkes"`, or `"kou_hawkes"`.

### 2. Devices and precision

Tensors have a device of `"cpu"` or `"metal"`. `to_device(t, device, token)`
is the only transfer to Metal and requires a valid `"gpu"` use capability;
`to_cpu(t)` is the explicit transfer back. Mixed-device arithmetic is an
error. Views preserve their base tensor's device.

An omitted ML device is `"auto"`. Auto chooses Metal only when it is
available, authorized, dtype-compatible, and the operation has a Metal
implementation; otherwise it chooses CPU. Explicit `"metal"` returns an error
instead of falling back. F64 is never silently downcast. Metal accepts f32,
f16, and bf16; f16/bf16 matrix and reduction accumulation and optimizer master
weights are f32.

Metal ML fitting and prediction cover linear, ridge, binary and multiclass
logistic, and dense neural models. Kalman, HMM, gradient-boosted-tree, and jump
models remain CPU-only: `"auto"` selects CPU and explicit `"metal"` returns a
structured `device_unsupported` error. The performance gate applies only to
the five eligible families.

During a Metal training step, parameters, the active batch, intermediates,
gradients, and optimizer state remain Metal-resident. Only bounded scalar
control values may return to the CPU. Device allocations and staging buffers
count against the existing 256 MiB VM limit.

### 3. Shared tensor operations

The tensor surface adds reshape, transpose, exp, log, sqrt, ReLU, softmax,
log-sum-exp, comparisons/masks, conditional selection, argmax, gather,
Cholesky solve, and seeded random construction. Existing element-wise
arithmetic, matmul, reductions, slicing, casting, and their autodiff rules
dispatch on the tensor device. These are host calls, not new opcodes.

The new numerical calls are:

- `cholesky_solve(matrix, rhs)` solves a real symmetric positive-definite
  rank-two system. `matrix` is square; `rhs` has shape `[n]` or `[n, k]` and
  the same dtype. Invalid shapes, non-finite inputs, or a failed positive-
  definite check are errors.
- `random_uniform(shape, seed)` returns an f64 tensor in `[0, 1)`.
- `random_normal(shape, seed)` returns an f64 standard-normal tensor.

Random shapes follow the existing tensor shape rules. A seed is an integer in
`[0, 2^53)`; the same function, shape, and seed produce byte-identical CPU
output in both VMs.

### 4. Replay and failure

CPU behavior retains its existing replay contract. Metal replay is defined for
the same seed, inputs, device family, precision, OS/runtime family, and Lana
version, within the documented dtype tolerance. Allocation, capability,
validation, cancellation, or instruction exhaustion exposes no partial model.

## Compatibility

- No source syntax changes.
- No new value kind: device storage extends `VAL_TENSOR`.
- No LABC layout or version change; new operations append host-call IDs.
- Existing tensors and training calls remain CPU and source-compatible.
- CUDA and non-Apple GPU backends are outside Lana 2.1.

## Acceptance

1. C and Rust CPU behavior remains differentially conformant.
2. Every ML family has tensor and dataset tests, invalid-input tests, and an
   uncertainty assertion.
3. CPU and Metal results agree within f32 `1e-5`, f16 `1e-3`, and bf16 `1e-2`.
4. Same-device replay stays within the corresponding tolerance.
5. On the release M4 candidate, each fixed representative eligible-family
   benchmark has a warmed median Metal time no greater than half its CPU time.
6. A failed acceptance item blocks 2.1 qualification.
