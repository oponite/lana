# LIP-020: Interactive REPL

- **Status:** Final
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Lana has `run` and `check` but no interactive mode. Every experiment is a
file, an edit, and a re-run. Python's universality owes a large debt to its
REPL: the immediate feedback loop is how people learn the language, prototype
a computation, and script a one-off. A language that requires a file for every
thought is slower to adopt and slower to explore.

This LIP adds a REPL as a thin loop over the existing compiler and VM. It adds
no language semantics and no LABC change; it is the cheapest high-leverage
adoption move available.

## Specification

### 1. Invocation

- `lana` with no subcommand, or `lana repl`, starts the REPL.
- The prompt is `lana> `; continuation lines use `...> `.

### 2. Session semantics

- Each input line (or completed statement) is compiled and executed in a
  persistent session. Top-level bindings persist across inputs.
- `STATE`, `STATE_DIST`, and `Information` values are first-class in the
  session: a bound state can be measured, sampled, and transformed in later
  inputs.
- A compile error prints the SYNTAX-10 recovery message (what is missing, the
  location, a valid example, available alternatives). A runtime error prints
  the stable error code, kind, and source span.

### 3. Commands

| Command | Effect |
|---|---|
| `:help` | list commands |
| `:quit` / `:exit` | end the session |
| `:load <file>` | compile and run a file in the current session |
| `:save <file>` | export the session's top-level bindings as a `.lana` file |
| `:clear` | drop all bindings |

- Commands are prefixed with `:` and are not Lana syntax.

### 4. Provenance and export

- REPL bindings carry the same provenance as source bindings. `:save` emits a
  `.lana` file that reproduces the session's bindings, so a REPL exploration
  can become a versioned, reviewable program.
- The session is deterministic given the same input sequence and seed; the RNG
  stream is per-session.

## Rationale

- **A thin loop, not a new evaluator.** The REPL reuses the existing compiler
  and VM; it is a driver, not a second implementation. This keeps the REPL's
  semantics identical to `run`.
- **Provenance-preserving export.** A REPL that cannot be turned back into
  source is a dead end. `:save` makes exploration durable and auditable,
  consistent with Lana's whole premise.

## Compatibility

- **CLI surface addition** (`lana repl`, bare `lana`). No existing command
  changes.
- **No LABC change, no language change, no VM change.**
- **Resource limits unchanged** (256 MiB, 50,000,000 instructions per input).

## Test coverage

- Session persistence: a binding defined in one input is usable in the next.
- State interaction: construct a `STATE`, then `measure`/`sample` it in a later
  input.
- Error recovery: a syntax error prints the SYNTAX-10 message and the session
  continues.
- Export: `:save` produces a file that `lana run` executes to the same result.
- Determinism: the same input sequence and seed produce the same session.
