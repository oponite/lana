# LIP-010: Incremental / online learning

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

## Motivation

Python's answer to new data is full retraining or awkward fine-tuning: the
training loop is a black box that either re-runs from scratch or mutates a
checkpoint in place, and neither is a value you can inspect or replay. There is
no notion of *which belief a new observation changed*.

Lana already has the two primitives this needs, separately:

- **Reactive Information** (`spec/SPEC.md` "Information", `papers/semantics.md`
  "Reactive ordinary Information") — `information(value)` creates a live
  dependency root; pure operations over it produce live derived values; a
  successful `observe` publishes one atomic revision and recomputes *only the
  affected pure nodes*.
- **Lazy datasets** (`spec/DATASETS.md`) — `lazy(fn, bound)` streams data
  without materializing the whole set.

This LIP wires the training primitive (LIP-006) into the reactive DAG so that a
new observation updates exactly the beliefs it touches, not the whole model.
The result is true online learning: the model is a live value, and new data is
an `observe` that recomputes the affected parameters — auditable, replayable,
and uncertainty-carrying, like every other Lana value.

## Specification

### 1. Reactive parameters

A training result (LIP-006 `VAL_TRAINING_RESULT`) whose `data` is a live
Information root produces **reactive parameters**: each parameter is a derived
Information value rooted in the data, not a frozen tensor.

- The step history is a reactive DAG. Each parameter node's inputs are the
  observations that produced its update; its output is the post-update value.
- The dependency is exact: a parameter depends on an observation if the
  observation contributes to its optimizer state or structural inputs, or if its
  gradient (LIP-011) or conditioning (LIP-009) is nonzero for it. A zero
  gradient at one point does not prove independence (Decision 7).
- Parameters retain provenance, replay, and uncertainty (LIP-006, LIP-008)
  exactly as in the batch case.

### 2. Incremental `observe`

```lana
let data  = information(lazy(fn, bound));   // live data root
let model = train(model_fn, data, loss, adam(learning_rate: 0.001));
observe(data, new_point);                   // one atomic revision
```

- `observe` on the data root publishes one atomic revision and recomputes only
  the affected parameter nodes — the ones whose derivation depends on the new
  observation. Unaffected parameters are untouched and retain their value and
  history.
- The recomputation is one (or a bounded number of) optimizer step(s) over the
  new observation, not a full retrain. The bound is a positive integer literal.
- For a Bayesian model (LIP-009), the incremental update is conditioning: the
  posterior is refined by the new evidence, and only the parameters the evidence
  touches are re-derived.

### 3. Explicit `update`

For a non-reactive (frozen) training result, an explicit incremental step is
provided:

```lana
let model2 = update(model, new_data, steps: 1);
```

- `update` returns a new `VAL_TRAINING_RESULT` whose step history extends the
  prior one; the prior result is unchanged (immutable, like `append`).
- `steps` is a positive integer literal; it bounds the optimizer steps applied
  to the new data.
- `update` is the non-reactive form of the same operation; the reactive form
  (§2) is `observe` on a live data root.

### 4. Provenance, replay, and audit

- Each incremental revision is a derivation node: its inputs are the prior
  revision and the new observation; its output is the post-update parameters.
  The full history — batch training followed by each incremental update — is a
  value, so you can ask *which observation changed which parameter, and by how
  much*.
- Deterministic replay (§9.7.5) covers the incremental run: the same
  `(seed, observation sequence, version)` reproduces the same parameter bytes.
- The reactive DAG is the audit trail: the set of recomputed nodes *is* the set
  of beliefs the new observation touched.

### 5. Errors

| Condition | Error |
|---|---|
| `observe` on a non-live (frozen) training result | `LANA_ERR_TYPE` |
| `update` on a non-training-result value | `LANA_ERR_TYPE` |
| `steps` not a positive integer | `LANA_ERR_INVALID_PARAMETERS` |
| new observation outside the data root's support | `LANA_ERR_INVALID_PARAMETERS` |
| non-finite loss or gradient during an incremental step | `LANA_ERR_INVALID_PARAMETERS` |

## Rationale

- **Reactive DAG, not a retrain loop.** The reactive Information machinery
  already recomputes exactly the affected pure nodes on `observe`. Making the
  training result's parameters reactive nodes means incremental learning is the
  *same* mechanism, not a new one — the "affected parts" are the dependency
  graph, computed exactly rather than approximated by a fine-tuning heuristic.
- **True online learning, not fine-tuning.** Python's fine-tuning re-runs the
  optimizer over a checkpoint with no record of what changed. Lana's incremental
  update is a value-producing revision with provenance, so the change is
  inspectable and replayable.
- **Sparse and structured models win exactly.** For a dense model a new
  observation touches every parameter (the gradient is dense), and the reactive
  DAG correctly recomputes all of them. For a sparse, structured, or Bayesian
  model — per-feature parameters, a posterior over a local belief — the DAG
  recomputes only the touched nodes. The mechanism is exact in both cases; the
  win is where the model's structure is local.
- **Inherited, not invented.** Reactive Information, lazy datasets, the training
  primitive, and Bayesian conditioning all already exist; this LIP composes them
  rather than adding a parallel system.

## Compatibility

- **No new `ValueType` tag** — reactive parameters are existing Information
  values over `VAL_TENSOR`; `update` returns the existing `VAL_TRAINING_RESULT`.
- **No LABC format change** — `update` is a host call; `observe` on a data root
  is the existing observation path. The bytecode version stays `2`.
- **New host-call ID** `update` appended to `LanaHostCallId` (C and Rust must
  match).
- **Depends on LIP-004** (tensor, lazy datasets), **LIP-006** (training
  primitive), **LIP-008** (uncertainty), and **LIP-009** (Bayesian conditioning
  as the incremental update for probabilistic models).
- **Resource limits unchanged**; the reactive DAG and revision history count
  against the 256 MiB limit.

## Test coverage

- Incremental `observe` recomputes only the affected parameter nodes for a
  sparse/structured model; unaffected parameters are byte-identical before and
  after.
- `update` extends the step history and leaves the prior result unchanged.
- A dense model recomputes all parameters (the gradient is dense) — the
  mechanism is correct even when nothing is skipped.
- Bayesian incremental update: conditioning on new evidence refines the
  posterior and touches only the parameters the evidence conditions.
- Provenance: the revision history records observation → parameter change.
- Replay: the same observation sequence reproduces byte-identical parameters.
- Errors: `observe` on a frozen result, non-positive `steps`, out-of-support
  observation, non-finite gradient.
- Differential conformance: byte-identical C11 vs Rust output for a fixed seed
  and observation sequence.
