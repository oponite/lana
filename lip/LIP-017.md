# LIP-017: Package manager and content-addressed registry

- **Status:** Draft
- **Author:** Vijay
- **Date:** 2026-09-05

- **Milestone:** Deferred from 2.1.0. Installed standard-library modules and
  existing local dependencies do not require a registry.

## Motivation

Imports are relative `.lana` paths only. There is no way to depend on another
package, pin a version, or share code across projects except by copying files.
Python's universality is inseparable from PyPI: the ecosystem flywheel is what
made it the default language, not the language itself. A language without a
package manager stays a toy; a language with one becomes a platform.

This LIP adds dependency declaration, deterministic resolution, and a
content-addressed registry. It builds on the fact that `lana.lock` already
records content identity — Lana's provenance philosophy is a natural fit for a
registry that pins dependencies by content, not by name.

## Specification

### 1. Dependency declaration

`lana.toml` gains a `[dependencies]` table:

```toml
[dependencies]
lana-http = "1.2.0"
lana-json = { version = "0.4.0", registry = "default" }
```

- A version requirement is a semver-compatible range (`"1.2.0"`, `"^1.2"`,
  `"~1.2.0"`).
- `registry` selects a registry; `"default"` is the public registry.

### 2. Resolution

- `lana add <name>`, `lana remove <name>`, and `lana update` edit
  `[dependencies]` and re-resolve.
- Resolution is deterministic: given the same `lana.toml` and registry state,
  the same dependency graph is produced. The resolver picks the highest
  version satisfying all constraints; a conflict is a hard error, never a
  silent pick.
- `lana.lock` records the resolved content identity of every transitive
  dependency. A build from a lockfile does not consult the registry and is
  byte-identical to the original.

### 3. Registry

- The registry is **content-addressed**: a package version is identified by the
  content identity of its source, not by a mutable name. Publishing the same
  name+version with different content is rejected.
- A package is a directory of `.lana` sources plus a `lana.toml`; the registry
  stores the content identity, the version, and the dependency metadata.
- `lana publish` verifies the package builds and tests clean before accepting
  it.

### 4. Import resolution

- `import pkg/module;` resolves `pkg` against the dependency graph, then
  `module` within that package. Relative imports (`import ./foo.lana`) are
  unchanged and resolve within the current package.
- Import cycles across packages are rejected, as today.

### 5. Provenance and capability

- A dependency is an external resource. Fetching it is an `external_call`
  effect and requires a `capability("registry")` grant (consistent with
  LIP-012's capability model). A build that only reads the lockfile and the
  local cache needs no network capability.

## Rationale

- **Content-addressed, not name-addressed.** Lana's whole value is auditable,
  reproducible reasoning. A registry that pins by content identity makes a
  dependency graph a replayable derivation, not a mutable pointer. This is the
  same reason `lana.lock` already records content identity.
- **Deterministic resolution.** A silent version pick is a reproducibility bug.
  Resolution is a pure function of the manifest and the registry snapshot.
- **Capability-gated fetch.** Fetching code is a consequential, outward-facing
  action; it should not happen without an explicit grant, matching Lana's
  secure-by-default stance.

## Compatibility

- **`lana.toml` schema** is extended additively (schema-1 remains readable; a
  manifest with `[dependencies]` is schema-2).
- **Relative imports are preserved**; the new `pkg/module` form is additive.
- **No LABC change**; this is a compiler-loader and CLI change.
- **Resource limits unchanged.**

## Test coverage

- Resolution: a manifest with a satisfiable range, an unsatisfiable range
  (hard error), and a transitive conflict.
- Lockfile determinism: two resolves from the same manifest produce identical
  lockfiles; a build from the lockfile is byte-identical with the registry
  offline.
- Cycle rejection across packages.
- Capability denial: a fetch without `capability("registry")` fails before
  network access.
- Publish: same name+version with different content is rejected.
